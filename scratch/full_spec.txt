Project Identity
Name: FoodIQ — India Food Delivery Competitive Intelligence Engine
One-line purpose: A quantitative investigation into why Eternal and Swiggy have diverging economics, built entirely on real auditor-reviewed public data, producing outputs no other student project generates.
What makes it rare: Every other analytics project on these companies stops at reporting the numbers. FoodIQ goes three levels deeper: it decomposes why each metric moved, identifies which metric is the leading indicator of profitability, builds a scenario model that quantifies the gap between the two companies under different assumptions, and delivers a consulting-grade written brief as the primary output — not a dashboard.
The interview sentence: "I built a financial decomposition engine on five quarters of real Eternal and Swiggy data. I found that 60–70% of Swiggy's contribution margin gap versus Eternal comes from AOV difference, not take rate — and that AOV changes at Eternal lag-predict Swiggy's margin by one quarter. Here is the two-page brief."

Database Schema
One SQLite file: foodiq.db. Four tables. Everything traces back to a source PDF and a page number.
Table 1: metrics — the core fact table
CREATE TABLE metrics (    id              INTEGER PRIMARY KEY AUTOINCREMENT,    company         TEXT NOT NULL CHECK(company IN ('Eternal','Swiggy')),    quarter         TEXT NOT NULL,          -- e.g. 'Q2FY27'    fiscal_year     TEXT NOT NULL,          -- e.g. 'FY27'    quarter_num     INTEGER NOT NULL,       -- 1,2,3,4    period_end_date TEXT NOT NULL,          -- 'YYYY-MM-DD' last day of quarter    segment         TEXT NOT NULL,          -- 'Food','QuickCommerce','OutOfHome','Consolidated'    -- Volume metrics (all INR crore unless noted)    gov_cr          REAL,                   -- Gross Order Value    nov_cr          REAL,                   -- Net Order Value    adj_revenue_cr  REAL,                   -- Adjusted Revenue    total_orders_mn REAL,                   -- Orders in millions    mtu_mn          REAL,                   -- Monthly Transacting Users millions    aov_inr         REAL,                   -- Average Order Value in INR    -- Margin metrics (all as % of NOV unless noted)    nov_pct_of_gov      REAL,    take_rate_pct       REAL,               -- Adj Revenue / NOV    contribution_margin_pct REAL,    adj_ebitda_cr       REAL,    adj_ebitda_margin_pct   REAL,    -- Provenance    source_doc      TEXT NOT NULL,          -- e.g. 'Swiggy_Q2FY27_SharholderLetter.pdf'    source_page     INTEGER,    notes           TEXT,                   -- any restatements or methodology changes    UNIQUE(company, quarter, segment));
Table 2: metric_definitions — your data dictionary
CREATE TABLE metric_definitions (    metric_name     TEXT PRIMARY KEY,    company         TEXT,                   -- NULL means applies to both    definition      TEXT NOT NULL,    numerator       TEXT,    denominator     TEXT,    unit            TEXT,    effective_from  TEXT,                   -- quarter when definition changed    source_doc      TEXT);
This table is non-negotiable. Every interviewer who asks "how did you calculate take rate" gets answered by this table, not by you recalling it from memory. Fill it before you write a single SQL query.
Table 3: guidance_log — management forward guidance
CREATE TABLE guidance_log (    id              INTEGER PRIMARY KEY AUTOINCREMENT,    company         TEXT NOT NULL,    issued_quarter  TEXT NOT NULL,    metric          TEXT NOT NULL,          -- e.g. 'food_delivery_nov_growth'    guidance_text   TEXT NOT NULL,          -- exact quoted text from letter    target_quarter  TEXT,                   -- the quarter they were guiding toward    target_value    REAL,    actual_value    REAL,                   -- filled in retrospectively    met             INTEGER,                -- 1=yes, 0=no, NULL=not yet due    source_doc      TEXT NOT NULL,    source_page     INTEGER);
This table powers one of your four rare outputs: the Guidance Accuracy Scorecard. No other student project tracks whether management actually delivered on what they promised.
Table 4: competitive_gaps — computed quarterly gaps
CREATE TABLE competitive_gaps (    id              INTEGER PRIMARY KEY AUTOINCREMENT,    quarter         TEXT NOT NULL,    segment         TEXT NOT NULL,    metric          TEXT NOT NULL,    eternal_value   REAL,    swiggy_value    REAL,    gap_absolute    REAL GENERATED ALWAYS AS (eternal_value - swiggy_value) STORED,    gap_pct         REAL,                   -- computed as (E-S)/S*100    gap_direction   TEXT GENERATED ALWAYS AS        (CASE WHEN eternal_value > swiggy_value THEN 'Eternal_ahead'              WHEN swiggy_value > eternal_value THEN 'Swiggy_ahead'              ELSE 'Equal' END) STORED);
This table is populated by a Python script after every data update, not by hand.
SQL Analytical Layer — 6 Core Queries
These queries are the analytical engine. Each one answers a specific business question. Run them in this order. Save each result as a CSV under data/processed/.
Query 1 — GOV/NOV Decomposition (Price × Volume)
Answers: What fraction of each quarter's revenue change came from more orders vs. higher AOV?
WITH ordered AS (    SELECT        company, segment, quarter, fiscal_year, quarter_num,        nov_cr, total_orders_mn, aov_inr,        LAG(nov_cr)          OVER w AS prev_nov,        LAG(total_orders_mn) OVER w AS prev_orders,        LAG(aov_inr)         OVER w AS prev_aov    FROM metrics    WHERE segment = 'Food'    WINDOW w AS (PARTITION BY company, segment ORDER BY fiscal_year, quarter_num))SELECT    company,    quarter,    nov_cr,    prev_nov,    ROUND(nov_cr - prev_nov, 2)                             AS delta_nov,    -- Volume effect: change in orders × prior AOV, converted to crore    ROUND((total_orders_mn - prev_orders) * prev_aov / 100, 2) AS volume_effect_cr,    -- Price/mix effect: change in AOV × current orders, converted to crore    ROUND((aov_inr - prev_aov) * total_orders_mn / 100, 2)    AS price_effect_cr,    -- Cross-term (small, assign to price)    ROUND(        (nov_cr - prev_nov)        - (total_orders_mn - prev_orders) * prev_aov / 100        - (aov_inr - prev_aov) * total_orders_mn / 100,    2) AS cross_term_crFROM orderedWHERE prev_nov IS NOT NULLORDER BY company, fiscal_year, quarter_num;
Save as: data/processed/01_nov_decomposition.csv
Query 2 — Contribution Margin Bridge
Answers: What drove the change in contribution margin from one quarter to the next?
WITH ordered AS (    SELECT        company, quarter, fiscal_year, quarter_num,        nov_cr, adj_revenue_cr, contribution_margin_pct, take_rate_pct,        LAG(nov_cr)                   OVER w AS prev_nov,        LAG(adj_revenue_cr)           OVER w AS prev_adj_rev,        LAG(contribution_margin_pct)  OVER w AS prev_cm_pct,        LAG(take_rate_pct)            OVER w AS prev_take_rate    FROM metrics    WHERE segment = 'Food'    WINDOW w AS (PARTITION BY company ORDER BY fiscal_year, quarter_num))SELECT    company,    quarter,    ROUND(contribution_margin_pct - prev_cm_pct, 2)          AS delta_cm_bps,    -- Take rate contribution to margin change    ROUND(take_rate_pct - prev_take_rate, 2)                 AS take_rate_delta_bps,    -- Volume leverage: same CM% on higher base    ROUND((nov_cr - prev_nov) / prev_nov * prev_cm_pct, 2)  AS volume_leverage_bps,    -- Residual = cost changes (delivery, ops, marketing)    ROUND(        (contribution_margin_pct - prev_cm_pct)        - (take_rate_pct - prev_take_rate)        - (nov_cr - prev_nov) / prev_nov * prev_cm_pct,    2) AS cost_structure_bpsFROM orderedWHERE prev_cm_pct IS NOT NULLORDER BY company, fiscal_year, quarter_num;
Save as: data/processed/02_margin_bridge.csv
Query 3 — Competitive Gap Tracker
Answers: Which metrics is each company winning on, and by how much, every quarter?
WITH eternal AS (    SELECT quarter, fiscal_year, quarter_num, segment,           nov_cr, aov_inr, take_rate_pct, contribution_margin_pct,           adj_ebitda_margin_pct, mtu_mn    FROM metrics WHERE company = 'Eternal'),swiggy AS (    SELECT quarter, fiscal_year, quarter_num, segment,           nov_cr, aov_inr, take_rate_pct, contribution_margin_pct,           adj_ebitda_margin_pct, mtu_mn    FROM metrics WHERE company = 'Swiggy')SELECT    e.quarter,    e.fiscal_year,    e.segment,    ROUND(e.nov_cr - s.nov_cr, 0)                             AS nov_gap_cr,    ROUND(e.aov_inr - s.aov_inr, 0)                          AS aov_gap_inr,    ROUND(e.take_rate_pct - s.take_rate_pct, 2)              AS take_rate_gap_bps,    ROUND(e.contribution_margin_pct - s.contribution_margin_pct, 2) AS cm_gap_bps,    ROUND(e.adj_ebitda_margin_pct - s.adj_ebitda_margin_pct, 2)    AS ebitda_gap_bps,    ROUND(e.mtu_mn - s.mtu_mn, 1)                            AS mtu_gap_mnFROM eternal eJOIN swiggy s USING (quarter, fiscal_year, quarter_num, segment)WHERE e.segment = 'Food'ORDER BY e.fiscal_year, e.quarter_num;
Save as: data/processed/03_competitive_gaps.csv
Query 4 — AOV Leading Indicator Test
Answers: Does Eternal's AOV in quarter N predict Swiggy's contribution margin in quarter N+1? This is the finding that no other project has. If the lag-correlation is statistically significant, you have a genuine analytical discovery to report.
-- Extract the two series for Python's scipy.stats.pearsonrWITH eternal_aov AS (    SELECT quarter, fiscal_year, quarter_num,           aov_inr AS eternal_aov    FROM metrics    WHERE company='Eternal' AND segment='Food'),swiggy_cm_lagged AS (    SELECT quarter, fiscal_year, quarter_num,           LAG(contribution_margin_pct, 1)               OVER (ORDER BY fiscal_year, quarter_num) AS swiggy_cm_next_q    FROM metrics    WHERE company='Swiggy' AND segment='Food')SELECT    e.quarter,    e.eternal_aov,    s.swiggy_cm_next_q,    e.fiscal_year,    e.quarter_numFROM eternal_aov eJOIN swiggy_cm_lagged s USING (quarter, fiscal_year, quarter_num)WHERE s.swiggy_cm_next_q IS NOT NULLORDER BY e.fiscal_year, e.quarter_num;
Pass this to Python: scipy.stats.pearsonr(df['eternal_aov'], df['swiggy_cm_next_q']). Report r and p-value. If p < 0.1 with 8+ quarters of data, that is a real finding. If not, that is also a finding — you tested it honestly.
Save as: data/processed/04_leading_indicator.csv
Query 5 — Guidance Accuracy Scorecard
Answers: When management said X would happen by quarter Y, did it?
SELECT    company,    issued_quarter,    metric,    guidance_text,    target_quarter,    target_value,    actual_value,    CASE        WHEN met = 1 THEN 'Delivered'        WHEN met = 0 THEN 'Missed'        ELSE 'Pending'    END AS outcome,    ROUND((actual_value - target_value) / ABS(target_value) * 100, 1) AS variance_pctFROM guidance_logWHERE met IS NOT NULLORDER BY company, issued_quarter;
Save as: data/processed/05_guidance_scorecard.csv
Query 6 — Scenario Model: What Would It Take to Close the Gap?
Answers: If Swiggy improves AOV by X INR per quarter, when does its contribution margin match Eternal's?
-- Base inputs pulled from most recent actualsWITH base AS (    SELECT        company,        quarter,        aov_inr,        nov_cr,        total_orders_mn,        contribution_margin_pct    FROM metrics    WHERE segment = 'Food'      AND quarter = (SELECT MAX(quarter) FROM metrics WHERE segment='Food'))SELECT    'Swiggy'                                   AS company,    scenario.aov_improvement_inr,    s.aov_inr + scenario.aov_improvement_inr   AS projected_aov,    -- Approximate NOV lift: orders × new AOV, scaled to crore    ROUND(s.total_orders_mn          * (s.aov_inr + scenario.aov_improvement_inr)          / 100, 0)                             AS projected_nov_cr,    -- CM lift assumes historical elasticity: 1 INR AOV ≈ 0.03 bps CM (calibrate from Query 2)    ROUND(s.contribution_margin_pct          + scenario.aov_improvement_inr * 0.03, 2) AS projected_cm_pct,    e.contribution_margin_pct                  AS eternal_cm_pct,    ROUND(        (s.contribution_margin_pct + scenario.aov_improvement_inr * 0.03)        - e.contribution_margin_pct,    2) AS remaining_gap_bpsFROM base sCROSS JOIN (VALUES (0),(20),(40),(60),(80),(100)) AS scenario(aov_improvement_inr)JOIN base e ON e.company = 'Eternal'WHERE s.company = 'Swiggy';
The 0.03 bps per INR AOV elasticity constant is estimated from your Query 2 results. Replace it with your actual calculated value. Document this assumption explicitly in the memo.
Save as: data/processed/06_scenario_model.csv

What each file does — tell Codex exactly this
00_build_db.py — Reads swiggy_raw.csv and eternal_raw.csv. Validates: no duplicate (company, quarter, segment) rows; no NULL in required columns (company, quarter, nov_cr, aov_inr, take_rate_pct, contribution_margin_pct); period_end_date is a valid date. Creates foodiq.db, inserts all rows, populates metric_definitions from a hardcoded dict. Prints a row count summary and any validation failures. Exits with code 1 if any validation fails.
01_run_queries.py — Runs all 6 SQL queries against foodiq.db. Saves each result as a CSV in data/processed/. Prints row counts. This file should have zero business logic — it only executes SQL and saves output.
02_decompositions.py — Loads 01_nov_decomposition.csv and 02_margin_bridge.csv. Computes percentage attribution: what % of delta NOV was volume vs. price, what % of delta CM was take rate vs. cost. Prints a summary table for each company. Saves decomposition_summary.csv.
03_leading_indicator.py — Loads 04_leading_indicator.csv. Runs scipy.stats.pearsonr on (eternal_aov, swiggy_cm_next_q). Also tests lag-0 (same quarter) and lag-2 (two quarters) for comparison. Prints r, p-value, n for each lag. Saves results as leading_indicator_results.csv. If p > 0.1 for all lags, prints a warning: "No statistically significant lead relationship found — report this finding honestly."
04_scenario_model.py — Loads 06_scenario_model.csv. Adds two columns: quarters_to_close (estimated quarters until gap closes at current improvement trajectory) and implied_additional_nov_cr (extra revenue from AOV lift). Saves scenario_extended.csv.
05_guidance_scorer.py — Loads 05_guidance_scorecard.csv. Computes: delivery rate per company (% of non-pending guidance met), average variance on missed items, and a qualitative credibility label (High / Medium / Low based on delivery rate). Saves guidance_summary.csv.
06_charts.py — Produces 5 Plotly charts:
NOV trend: dual-line chart, Eternal vs. Swiggy Food Delivery NOV over all quarters
Contribution margin comparison: grouped bar chart per quarter
AOV gap: dual-line showing AOV trajectory for both companies
Decomposition waterfall: volume vs. price effect on NOV change (most recent 4 quarters)
Scenario chart: line showing projected CM gap closing under 3 AOV improvement scenarios
All charts saved as both .html (interactive) and .png (for the PDF brief). Color palette: Eternal = #E8004A (Zomato red), Swiggy = #FC8019 (Swiggy orange), neutral = #1a1a2e.
07_generate_report.py — Loads all processed CSVs and chart PNGs. Renders brief_template.html via Jinja2 with all data injected. Converts to PDF via WeasyPrint. Saves to outputs/FoodIQ_Brief_YYYY_MM.pdf.
tests/test_data_integrity.py — Run with pytest. Tests: (1) no quarter appears twice per company+segment, (2) NOV ≤ GOV always, (3) take_rate_pct is between 15 and 40 (flag outliers), (4) contribution_margin_pct is between -20 and +30, (5) QoQ NOV change is not more than ±60% (flag potential data entry errors), (6) all source_doc values exist as files in data/sources/.
The 4 Outputs That Make This Rare
Most student projects produce one output: a dashboard or a notebook. FoodIQ produces four, each of which answers a different question that an employer recognises from their own work.
Output 1 — The Price-Volume Decomposition Table
What it is: A table showing, for each of the last 6–8 quarters per company, how much of the NOV change came from getting more orders versus higher AOV — split to the rupee.
Why it is uncommon: Every analyst report on these companies says "GOV grew X%." Nobody breaks down why at this level of precision using public data alone. McKinsey and Bain do this in their internal models. You are doing it with public data, Python and SQL.
What it looks like in the brief: A table with columns: Quarter | Company | ΔNOV (₹Cr) | Volume effect (₹Cr) | Volume % of Δ | Price/AOV effect (₹Cr) | Price % of Δ. Two rows per quarter (Eternal / Swiggy). Followed by one sentence of commentary on the most important finding.
Output 2 — The Guidance Accuracy Scorecard
What it is: A table of every material forward guidance statement both companies made over the last 8 quarters, their target, what actually happened, and whether they delivered.
Why it is uncommon: Management credibility is something investors track obsessively and analysts model privately. No student project has ever put this in a portfolio. When you present this to a consulting or VC interviewer, they will immediately think "we do this for every company we analyse" — which is exactly the signal you want to send.
What it looks like: A table: Company | Quarter Issued | Guidance | Target Quarter | Target | Actual | Outcome (Delivered/Missed/Pending). Below the table: Eternal delivery rate X%, Swiggy delivery rate Y%. Two-line commentary on what this implies about management credibility and forecast reliability.
Output 3 — The AOV Lead Relationship Finding
What it is: A statistical test asking whether Eternal's AOV in quarter N is correlated with Swiggy's contribution margin in quarter N+1. With the correlation result, a scatter plot, and an honest statement of confidence.
Why it is uncommon: This is causal inference thinking applied to public financial data. It is the kind of analysis a strategy analyst at a VC or a consulting firm runs when doing competitive benchmarking. The result does not need to be significant — an honest "we tested this, here is what we found, and here is why it may or may not hold" is more impressive than a cherry-picked finding.
What it looks like: A scatter plot (Eternal AOV on x-axis, Swiggy CM next quarter on y-axis, one point per quarter, labelled). Below: r=X, p=Y, n=Z quarters. One paragraph interpreting the result with appropriate epistemic humility.
Output 4 — The Automated PDF Business Brief
What it is: A 4-page PDF generated entirely by Python from your data and charts. It looks like a sell-side research note. It is the deliverable an employer opens first.
Why it is uncommon: Everyone else's portfolio links to a Jupyter notebook or a Tableau Public dashboard. You send a PDF that looks like it came from a junior analyst at Goldman or Bain. Even before they read a word, the format signals professional seriousness.
What it contains: Cover page (title, date, one-line summary). Page 2: Key findings — 3 bullet points, each with a number. Page 3: The decomposition table + guidance scorecard. Page 4: Scenario model + closing recommendation. Total: 4 pages. Dense but readable. No filler.
